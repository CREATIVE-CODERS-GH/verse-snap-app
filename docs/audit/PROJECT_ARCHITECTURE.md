# Verse Snap — Project Architecture

*Audit date: 2026-10-19 · Branch: `migration/independent-supabase` · Method: code inspection plus `tsc`, `eslint`, `npm audit` (the app was not run and nothing was tested in a browser).*

## 1. What it is
A mobile-first Bible reader. You say, scan, or type a verse reference (or describe a verse in plain language) and the app opens it. Guests can use everything; signing in syncs saved verses and history to Supabase.

## 4. Request flow
1. **Bible lookup (main path):** typed/voice/OCR text → `classify-query` / `parse-reference` → `bibleService` → HelloAO `GET /api/{apiId}/{BOOK}/{chapter}.json` directly **from the browser** (book metadata is fetched per edition, per AGENTS.md). Cached in `chapter-cache.ts`, React Query, and the Workbox `vs-bible-api` cache (30 days, 200 entries).
2. **Natural-language search:** client calls server fn `searchScripture` → server calls Lovable AI Gateway for *references only* → verse text is re-fetched from HelloAO and ranked. In-memory cache (100 entries) and in-memory rate limit (20/min/IP) — per-instance, not shared.
3. **Auth:** email+password and password reset use `supabase.auth` directly. Google OAuth goes through `@lovable.dev/cloud-auth-js`, then `supabase.auth.setSession(tokens)`.
4. **Library sync:** `library.ts` talks to `saved_verses` / `history` straight from the browser under RLS. No server code is involved.
5. **Server-function auth plumbing** (`attachSupabaseAuth` → `requireSupabaseAuth`) exists, but **no server function currently uses `requireSupabaseAuth`**, and `supabaseAdmin` / `authenticateCronRequest` are unused (grep found no callers outside `src/integrations`).

## 5. Database (from migrations only — live DB NOT inspected)
| Table | Purpose | RLS | Used by app? |
|---|---|---|---|
| `profiles` (id→auth.users, display_name, translation, text_size, theme) | per-user prefs | own-row ALL | **No** — prefs are localStorage-only |
| `translations` (code, name, language, sort_order; seeded KJV only) | translation list | public SELECT | **No** — settings reads `BIBLE_TRANSLATIONS` from code |
| `saved_verses` | bookmarks, UNIQUE(user, translation, book, chapter, verse) | own-row ALL | Yes |
| `history` | recently viewed | own-row ALL | Yes |
| trigger `on_auth_user_created` → `handle_new_user()` (SECURITY DEFINER, EXECUTE revoked) | auto-create profile | n/a | Yes (implicit) |

All three migration files are dated 2026-09-10 and were generated by Lovable.

## 6. Key observations (by risk)
- **HIGH — Hosting target is Cloudflare, chosen implicitly by the Lovable config wrapper**, not declared in this repo. Moving off Lovable means choosing a host deliberately.
- **HIGH — Core build config lives in a Lovable-owned package** (`@lovable.dev/vite-tanstack-config`); removing it means re-declaring plugins by hand.
- **MEDIUM — Dead/unused backend surface:** `profiles`, `translations`, `requireSupabaseAuth`, `supabaseAdmin`, cron auth. Decide whether to wire up or drop before migrating.
- **MEDIUM — Translation code drift:** DB default `'KJV'` vs app code `'KJAV'`. `resolveTranslation` maps KJV→KJAV, but `library.isSaved/unsave` filter on the literal translation string, so pre-existing rows saved as `KJV` may not be found/removed when the app uses `KJAV`. Needs a data check and probable backfill during migration.
- **LOW — `src/routes/README.md`, `.lovable/` notes and `README.md`/`roadmap.md`** contain the original Lovable prompts, not setup documentation.
- **LOW — `eng.traineddata` (512 KB) is committed at repo root** but not referenced by the code (see FEATURE_AUDIT).
